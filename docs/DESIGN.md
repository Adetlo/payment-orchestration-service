# Design specification

This document is the contract between the backend, the demo UI, the infrastructure files and the
documentation. It is written before the code and kept in sync with it. Everything here is
synthetic: there are no real accounts, payment networks or employer systems.

## 1. Goals

A production-style **payment orchestration service** that accepts payment instructions over REST,
persists them with strict idempotency, drives a payment state machine through Kafka events using the
transactional outbox pattern, retries transient failures with bounded exponential backoff, dead-letters
poison messages, reconciles internal records against a synthetic settlement feed, keeps an append-only
audit trail, and exposes structured logs, health and Prometheus metrics. A small React UI makes the
behaviour visible.

Branding: **PAYMENT ORCHESTRATION LAB**. No real bank branding.

## 4. Backend

### 4.1 Stack and conventions

* Java 21, Spring Boot 3.4.x, Maven. Base package `io.github.adetlo.payments`.
* Package-by-feature: `domain` (pure, no Spring), `application` (services, state machine, ports),
  `infrastructure` (JPA, Kafka, Redis, scheduling, settlement simulator), `api` (controllers, DTOs,
  error handling), `config`, `observability`.
* Money: `Money(BigDecimal amount, Currency currency)`; scale enforced per currency
  (GBP/EUR/USD/SGD 2, JPY 0, IDR 0); `RoundingMode.UNNECESSARY` when constructing (reject wrong scale),
  never `double`/`float`. Max amount 1,000,000.00 per payment in the demo rules.
* IDs are UUIDv4 strings in the API; `paymentId` is generated by the service.
* Timestamps are UTC ISO-8601 (`Instant`).
* Errors: RFC 7807 `application/problem+json` via `ProblemDetail`; never a stack trace; every response
  carries `X-Request-Id` and `X-Correlation-Id` (echoed from the request if present, else generated).
* Flyway migrations in `db/migration` (V1__payments.sql ... ). Hibernate `ddl-auto=validate`.
* Profiles: `local` (default; localhost infra), `docker` (compose hostnames, JSON logs),
  `demo` (enables `X-Demo-Failure` injection and synthetic seed helpers), `test`, `prod` (failure
  injection hard-disabled, Swagger UI off, JSON logs).

### 4.2 Domain model

| Type | Fields (essential) |
|------|--------------------|
| `Payment` (aggregate) | paymentId, instruction (`PaymentInstruction`), status (`PaymentStatus`), failureReason (nullable), retryCount, maxRetries (3), nextRetryAt, demoFailureMode (nullable, demo only), idempotencyKey (nullable), correlationId, createdAt, updatedAt, version (optimistic lock) |
| `PaymentInstruction` | payerAccount (`AccountReference`), payeeAccount (`AccountReference`), money (`Money`), reference (1..35 chars, `[A-Za-z0-9 ./-]`) |
| `AccountReference` | value matching `^[A-Z]{2}[0-9]{2}[A-Z0-9]{8,30}$` (synthetic IBAN-like) |
| `PaymentStatus` | RECEIVED, VALIDATED, PROCESSING, COMPLETED, REJECTED, FAILED, RETRY_PENDING, CANCELLED |
| `PaymentEvent` | eventId, paymentId, eventType, eventVersion (1), occurredAt, fromStatus, toStatus, details (JSON) , correlationId |
| `AuditEntry` | id, paymentId (nullable for reconciliation), action, actor (`system`/`api`/`scheduler`/`consumer`), details JSON, occurredAt. Append-only: no update/delete in the repository and a DB trigger rejects UPDATE/DELETE. |
| `OutboxEvent` | id, aggregateType, aggregateId, eventType, eventVersion, payload (JSON envelope), status NEW/PUBLISHED/FAILED, attempts, nextAttemptAt, lastError, createdAt, publishedAt |
| `IdempotencyRecord` | idempotencyKey (PK), requestHash (SHA-256 of canonical JSON body), paymentId, responseStatus, responseBody, state IN_PROGRESS/COMPLETED, createdAt, expiresAt (24h) |
| `ReconciliationRun` | runId, startedAt, completedAt, status RUNNING/COMPLETED/FAILED, scenario, recordsChecked, matched, unmatched, counts per classification |
| `ReconciliationItem` | id, runId, paymentId (nullable), externalReference, classification MATCHED/AMOUNT_MISMATCH/MISSING_INTERNAL/MISSING_EXTERNAL/STATUS_MISMATCH, internalAmount, externalAmount, internalStatus, externalStatus, details |

### 4.3 State machine (explicit transition table)

```
RECEIVED      -> VALIDATED | REJECTED | CANCELLED
VALIDATED     -> PROCESSING | CANCELLED
PROCESSING    -> COMPLETED | RETRY_PENDING | FAILED
RETRY_PENDING -> PROCESSING | FAILED | CANCELLED
COMPLETED, REJECTED, FAILED, CANCELLED : terminal
```
`PaymentStateMachine.transition(payment, target)` validates and throws `InvalidStateTransitionException`
(HTTP 409 `about:blank#invalid-state-transition`) otherwise. Every transition writes a `PaymentEvent`,
an `AuditEntry` and (for the externally visible ones) an `OutboxEvent` in the **same transaction**.

### 4.4 Processing flow (event-driven)

1. `POST /api/v1/payments` -> validate request (Bean Validation + domain rules) -> idempotency check
   -> in one DB transaction: insert `payments` (RECEIVED), `payment_events`, `audit_entries`,
   `outbox_events` (`PaymentReceived`), idempotency record COMPLETED -> 201.
2. `OutboxPublisher` (scheduled every 500 ms, batch 50, `SELECT ... FOR UPDATE SKIP LOCKED`) publishes
   NEW events to Kafka topic `payment.events.v1` (key = paymentId, so one payment is ordered), marks
   PUBLISHED; on send failure increments attempts with backoff 1s,2s,4s,8s,16s (max 5) then FAILED.
3. `PaymentProcessingConsumer` (group `payment-processor`) consumes `payment.events.v1`:
   * on `PaymentReceived`: business validation (payer != payee, currency supported, amount within
     limits, reference present) -> VALIDATED + `PaymentValidated` or REJECTED + `PaymentRejected`;
     then immediately starts processing: VALIDATED -> PROCESSING, calls `SettlementGateway`.
   * `SettlementGateway` (port) has a `SimulatedSettlementGateway` adapter: returns SETTLED normally;
     honours `demoFailureMode` on the payment when profile `demo` is active:
     `settlement-timeout` (transient: fails first 2 attempts then succeeds), `settlement-rejected`
     (permanent -> FAILED immediately), `poison-message` (consumer throws, record goes to DLT).
   * success -> COMPLETED + `PaymentCompleted`; transient failure -> RETRY_PENDING with
     `nextRetryAt = now + 2^retryCount * 1s` (cap 30 s) + `PaymentRetryScheduled`; retries exhausted or
     permanent failure -> FAILED (failureReason) + `PaymentFailed`.
   * Consumer is idempotent: it re-reads the payment and ignores events whose status no longer applies.
4. `RetryScheduler` (every 1 s) picks RETRY_PENDING payments with `nextRetryAt <= now`
   (`SKIP LOCKED`, batch 20), moves them to PROCESSING and calls the gateway again (same logic as 3).
5. Kafka consumer errors use `DefaultErrorHandler` with 3 attempts (backoff 500 ms) and a
   `DeadLetterPublishingRecoverer` to `payment.events.v1.dlt`. Dead-lettered records are counted
   (`payment_dead_letter_total`) and logged with the paymentId.
6. `POST /api/v1/payments/{id}/cancel` -> allowed from RECEIVED, VALIDATED, RETRY_PENDING ->
   CANCELLED + `PaymentCancelled`.
7. Reconciliation (`POST /api/v1/reconciliation/run`): `SyntheticSettlementFeed` builds external records
   from the current COMPLETED/FAILED payments; `scenario=clean` (default) matches everything;
   `scenario=with-discrepancies` deterministically (seeded) perturbs: 1 AMOUNT_MISMATCH, 1
   MISSING_INTERNAL (extra external record), 1 MISSING_EXTERNAL (one completed payment dropped),
   1 STATUS_MISMATCH (a FAILED payment reported settled) when enough payments exist. Produces a run,
   items, audit entry, `ReconciliationCompleted` on `reconciliation.events.v1`, metrics.

### 4.5 Idempotency (POST /api/v1/payments)

* Header `Idempotency-Key` (optional, 1..128 chars). Without it every request creates a payment.
* With it: acquire a short Redis lock `idem:{key}` (SET NX PX 10000). If Redis is unavailable, log a
  warning and continue: the DB unique constraint on `idempotency_records.idempotency_key` is the
  source of truth (fail-safe, never fail-open on duplicates).
* Look up the record:
  * none -> insert IN_PROGRESS (unique constraint; on `DataIntegrityViolation` re-read and treat as
    existing) -> create payment -> store responseStatus/body, state COMPLETED.
  * exists, same requestHash, COMPLETED -> return the stored response (same status 201, same body,
    header `Idempotent-Replayed: true`).
  * exists, different requestHash -> 409 problem `idempotency-key-reuse`.
  * exists, IN_PROGRESS (concurrent) -> 409 problem `idempotency-request-in-progress` with `Retry-After: 1`.
* Records expire after 24 h (cleanup job hourly).

### 4.6 Event envelope (Kafka, JSON)

```json
{
  "eventId": "uuid", "eventType": "PaymentCompleted", "eventVersion": 1,
  "occurredAt": "2026-10-22T10:15:30.123Z", "paymentId": "uuid", "correlationId": "uuid",
  "data": { "status": "COMPLETED", "amount": "125.50", "currency": "GBP", "reference": "INV-1001",
            "fromStatus": "PROCESSING", "retryCount": 0, "failureReason": null }
}
```
Event types: PaymentReceived, PaymentValidated, PaymentRejected, PaymentRetryScheduled,
PaymentCompleted, PaymentFailed, PaymentCancelled, ReconciliationCompleted. Account numbers are
**not** included in events (masked `payerAccountMasked: "GB**...1234"` only).

### 4.7 REST API (all JSON, prefix `/api/v1`)

| Method & path | Request | Response |
|---|---|---|
| `POST /payments` | body `{payerAccount, payeeAccount, amount: "125.50", currency: "GBP", reference}`; headers `Idempotency-Key?`, `X-Demo-Failure?` (demo profile only: `settlement-timeout`, `settlement-rejected`, `poison-message`) | `201` `PaymentResponse`, `Location: /api/v1/payments/{id}`; `400` validation problem; `409` idempotency problems |
| `GET /payments?status=&currency=&from=&to=&page=0&size=20` | `from`/`to` are ISO instants on `createdAt` | `200` `{items: PaymentResponse[], page, size, totalElements, totalPages}` sorted createdAt desc |

| `GET /payments/{id}/events` | | `200` `{paymentId, events: PaymentEventResponse[], audit: AuditEntryResponse[]}` oldest first |
| `POST /reconciliation/run` | `{scenario: "clean" \| "with-discrepancies", seed?: 42}` | `202`? No: `200` `ReconciliationRunResponse` (runs synchronously, small) |


`ReconciliationRunResponse`: `{runId, scenario, status, startedAt, completedAt, recordsChecked, matched,

### 4.8 Database (Flyway)

Tables: `payments`, `payment_events`, `idempotency_records`, `outbox_events`, `audit_entries`,
`reconciliation_runs`, `reconciliation_items`. Indexes: `payments(status)`, `payments(created_at desc)`,
`payments(currency, created_at)`, `payment_events(payment_id, occurred_at)`,
`outbox_events(status, next_attempt_at)`, `audit_entries(payment_id, occurred_at)`,
`reconciliation_items(run_id)`, `idempotency_records(expires_at)`. Trigger
`audit_entries_append_only` raises on UPDATE/DELETE. Amounts are `NUMERIC(19,4)`; currencies `CHAR(3)`.

### 4.9 Redis (why)

Redis is used for two things only: (1) the short-lived idempotency lock that serialises concurrent
requests with the same key before the DB constraint is reached, and (2) a simple fixed-window rate
limit on `POST /api/v1/payments` (default 200 req/min per client IP, disabled in `test`). Both degrade
safely when Redis is down (the DB constraint still guarantees a single payment; rate limiting is skipped
with a warning and `redis` reports DEGRADED in `/system/health`).

### 4.10 Observability

* Logback: human-readable console in `local`/`test`; JSON (logstash encoder) in `docker`/`prod`.
  MDC keys `correlationId`, `requestId`, `paymentId` where known.
* Micrometer (Prometheus names; the Prometheus client reserves the `_created` suffix, so the creation
  counter is `payment_received_total`): `payment_received_total`, `payment_completed_total`, `payment_failed_total`,
  `payment_rejected_total`, `payment_cancelled_total`, `payment_retry_total`,
  `payment_dead_letter_total`, `payment_processing_duration_seconds` (timer, RECEIVED -> terminal),
  `outbox_pending` (gauge), `outbox_failed` (gauge), `outbox_published_total` (counter),
  `reconciliation_runs_total`, `reconciliation_mismatch_total{classification}`,
  `idempotency_replay_total`, `idempotency_conflict_total`.
* Health indicators: db (built-in), kafka (AdminClient `describeCluster` with 2 s timeout), redis.

### 4.11 Security (demo level, documented honestly)

Bean Validation on every input; ProblemDetail responses with no internal detail; security headers
filter (`X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy`,
`Cache-Control: no-store` on API); CORS allowed only for `http://localhost:3000` and `:5173`;
request body limit 64 KB; no authentication (stated limitation; a note describes where OAuth2 resource
server would go); Docker runs as non-root; CI runs Trivy (dependency/container) and CodeQL; Dependabot.

## 5. Frontend (demo UI)

Vite + React 18 + TypeScript strict, React Router, no heavy UI library (hand-written CSS with tokens,
light theme, IBM Plex-like system font stack). API base `/api/v1` (Vite dev proxy to `localhost:8080`;
nginx proxy in Docker). Pages: Dashboard (`/`), Create payment (`/payments/new`), Payments list
(`/payments`), Payment detail (`/payments/:id`), Reconciliation (`/reconciliation`), System health
(`/health`). Header brand "PAYMENT ORCHESTRATION LAB", left nav, status pills with colours:
COMPLETED green, FAILED/REJECTED red, PROCESSING/RETRY_PENDING amber, RECEIVED/VALIDATED blue,
CANCELLED grey. Polling every 3 s on dashboard/detail/health (no websockets). Vitest + Testing Library
tests for: status pill mapping, create-payment form validation and submit (mocked fetch), payment
detail timeline rendering, dashboard stats rendering. `data-testid` attributes on key elements so the
Playwright screenshot script can wait for data.

## 6. Demo and screenshots

* `scripts/demo.sh`: `docker compose up -d --build` (unless `--no-start`), wait for
  `/api/v1/system/health` UP, then run the scripted scenario with curl + jq, printing readable sections.
* `scripts/seed-demo.sh`: deterministic synthetic data (12 payments across GBP/EUR/USD/SGD, including one
  `settlement-timeout` retry, one `settlement-rejected`, one cancelled, one idempotent replay), then a
  `with-discrepancies` reconciliation run. Idempotency keys `demo-seed-001..012` so re-running is safe.
* `e2e/` Playwright (chromium, 1440x900, deviceScaleFactor 1): captures the eight images into
  `docs/images/`. `scripts/capture-screenshots.sh` orchestrates start -> seed -> capture -> stop.

## 7. Testing strategy (backend)

JUnit 5, AssertJ, Mockito, Awaitility, Testcontainers (postgres:16-alpine, apache/kafka:3.9.1,
redis:7-alpine) shared via a singleton `IntegrationTestSupport` base class. Categories: unit (domain,
state machine, money, envelope, hashing), service (mocked ports), repository/JPA (Postgres container),
API (MockMvc + full context), idempotency (sequential + 20-thread concurrent), outbox publisher, Kafka
consumer end-to-end, retry/failure injection, reconciliation scenarios, validation/problem responses,
actuator/metrics. JaCoCo report at `backend/target/site/jacoco`. Spotless (google-java-format AOSP
style), SpotBugs (`spotbugs-maven-plugin`, effort max, threshold medium), no PMD.
